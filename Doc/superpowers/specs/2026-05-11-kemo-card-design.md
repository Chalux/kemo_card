## 1. 目标与约束

### 1.1 产品形态

- **双线并存**：单人线与联机线均保留；**当前里程碑只打磨单人线**，联机框架必须预留但不以联机体验绑架首发乐趣。
- **单人幻想**：指挥官——一人统筹四槽角色、构筑与出牌；不是「假装四人房各点一遍」。
- **管道统一、体验可分叉**：
  - **统一**：可序列化权威状态、槽位索引、指令、`characterIndex` 等联机就绪管道。
  - **可分叉**：单人 UI / 奖励分发 / 金币可走指挥官路径；联机再切分槽规则。
- **当前里程碑**：本地单人；规则上操控 **4 名上阵角色** 对抗 **AI 敌人**。真联机（房间、掉线接管、多人金币协议等）**不在本里程碑实现**。
- **卡牌双层模型**（细则见第 4.6 节）：
  - **Run 层**：全队共享 `CardCollection`（解锁模型；单人/联机皆共享）。
  - **战斗层**：每名角色 **独立牌库、手牌、弃牌堆**。
- **Roguelike 进程**：采用 **环模型**（见第 4 节）；Run 开始前必须选择 **故事脚本**（每 Run 唯一）。
- **首发压力定位（轻死亡、重路线）**：战斗失败无资源税、构筑非战斗可随时调整；局内不可逆压力主要来自 **账本出池**、**卡牌升级链推进**、**角色潜能推进** 等路线向变化，而非死亡惩罚。

### 1.2 工程约束（与仓库规则对齐）

- **游戏本体**：仓库内 **纯 C#**（Godot Mono）。
- **Mod 脚本**：可使用 **Lua / TypeScript / Python** 等，由 **C# 脚本宿主**统一加载与沙箱化 API。
- **组合优先于继承**：管理器与系统服务以组合方式拼装（不在本文展开类图）。
- **对话系统**：叙事对话 UI 预定采用 Godot 插件 **Dialogue Manager**（[nathanhoad/godot_dialogue_manager](https://github.com/nathanhoad/godot_dialogue_manager/tree/main)，面向 Godot 4.6+）。插件以 addon 形式接入；游戏侧用 **C# 桥接**消费其运行时。Dialogue Manager 负责对话演出层；Run 上的故事脚本 / 事件选项逻辑由宿主与 Mod 脚本负责，二者分责，不互相替代。

## 2. 总体架构与宿主/Mod 分界

### 2.1 七大管理器（权威注册中心）

下列管理器各自囊括该类对象定义，**由配置决定**，并支持 **动态注册**；凡 **未注册** 的引用一律 **非法**：

1. 角色  
2. 战斗  
3. 事件  
4. 卡牌  
5. 道具（主要为药水等消耗品；**细则见商店·道具规格**，本规格只保留注册与非法语义占位）  
6. 技能  
7. Buff  

**刷新时机**：仅在 **游戏启动** 或 **Mod 启用/禁用** 时更新管理器内容；运行期对定义池 **只读**。

### 2.2 非法语义与 Buff / 被动来源

- **非法技能**：执行时 **无操作**（可记录诊断日志）。
- **非法 Buff**：**不挂载**。
- **单位 Buff / 队伍领域**：一律只允许经 **技能** 尝试添加。效果、事件、道具、开战注入若需上 Buff/领域，必须设计为 **触发技能**（开战释放 / 使用时释放），禁止内容侧直写战斗状态绕过技能。
- **卡牌 / 角色** 可映射到一个或多个技能；角色主动链见战斗规格中的 `activeSkillChain`。
- **角色被动**：以 **buff 为唯一载体**，挂钩 `onWaveStart / onTurnStart / onActiveSkillCast / onSlotCardPlayed` 等多触发点（开战仍注入一次）；见 [战斗规格「buff 运行时」](./2026-07-21-combat-system-design.md) 与本文 §4.5.2–4.5.3。
  > 【2026-09-21 合并】原「被动 = 潜能门闩解锁后的自动技能，首发仅在 BattleStart 触发一次」的表述已废弃（历史正文见归档的 buff/潜能规格）。
- **BattleStart 自动技能顺序**（可复现、写死）：
  1. **被动**：上阵槽位 `0 → 3`；同一角色内按 `requiredPotential` 档位 **低 → 高**；各尝试一次。
  2. **共享 Run 修饰**（见 4.7）：按列表 **插入序**；各尝试一次；再按 charges 规则在胜利结算时扣减。

### 2.3 C# 核心职责

- **运行态服务**：`RunController` 编排、战斗模拟（细节见战斗规格）、Run 账本、存档门闩等。
- **脚本宿主（Script Host）**：
  - 向 Mod 脚本暴露 **受控 API**（白名单命令 + 只读查询）。
  - 禁止脚本直接操控引擎对象图；脚本输出必须是 **可校验的结构化 DTO**。
  - **随机性**：与 Run / 战斗相关的随机必须使用 **宿主派生的 RNG 流**；脚本禁止自带会破坏可复现性的随机源。

### 2.4 关键原则

- **单一事实源**：注册表在 C#；脚本只 **提议**，宿主 **校验 + 原子提交**。
- **不可逆门闩**：与账本相关的写入必须发生在宿主判定的 **不可逆提交点**（见 4.3 / 5.3）。
- **可复现**：优先队列平局、洗牌、选项生成等均绑定 Run 种子派生 RNG。

## 3. 战斗（摘要）

战斗为独立权威规格，本文只保留与 Run / 内容边界相关的摘要：

- **阶段**：玩家阶段 → 卡牌执行阶段 → 敌方阶段 → 循环。
- **生命**：队伍 **共享 HP** 为唯一玩家生命账本；`MaxSharedHp = sum(上阵角色当前 MaxHealth)`（可中途重算）；归零败北。
  - 玩家角色 **无 Health 当前值**（仅 MaxHealth）；无单角色倒地；残血条件走 Shared。
  - **SharedHp 仅存在于战斗内**；非战斗无「当前共享血量」。
  - **开战时**被动/修饰 **禁碰 SharedHp**，结算后重算 `MaxSharedHp` 并 **补满**；同场多波跨波保留。
  - 点选仍可点槽位；分槽伤害分算后扣 Shared；另有 Team/Shared 直伤（一次）；治疗仅 Team/Shared（禁止点名队友回血）。
- **主动技**：每角色 `activeSkillChain`（基础 + 蓄力）+ 战斗内计数器；放第 k 档扣累计 `T_k`；不占「已行动」。
- **被动技 / 修饰**：见 2.2 / 4.5 / 4.7；BattleStart 先被动后修饰，再开局满手。
- **卡牌经济**：当前能量 / 当前可用能量；**入队=手牌标记**（不离手）；手牌 5；开局满手，此后按抽牌公式；禁止中途即时抽牌；`priority` 越大越先。
- **封印 / 弃牌**：见战斗规格（封印清标记并禁主动；弃牌分主动与随机未标记两通道）。

完整规则、状态机、指令与回合开始管线 → **[2026-07-21-combat-system-design.md](./2026-07-21-combat-system-design.md)**。

## 4. Roguelike：环模型、账本、角色与卡牌

> 权威循环对齐 `run-mod`：**Event → Reward → … → Battle → BattleEnd → RingEnd**。旧「自由节点图」表述废弃；远期若恢复节点图，须另开规格且不得与本节冲突而不声明。

### 4.1 Run 启动与故事脚本

- Run 开始前 **必须** 选择 **故事脚本**（唯一）。
- Run 固化：种子、故事脚本 id、环/进度上下文、管理器版本摘要（用于诊断）。
- **故事脚本实现形态（混合，底线数据驱动）**：
  - **底线**：环覆盖、事件池、战斗池、胜利条件等可用配置 / DTO + 宿主钩子跑通一局，不依赖通用脚本语言。
  - **扩展**：复杂选项分支、演出钩子等再进 Mod 脚本。
  - **禁止**脚本驱动顶层状态机跳转；内容覆盖仅限宿主白名单，且 **不得绕过非法校验**。
- **内容自洽义务**（Fatal 与玩法终局分轨）：
  - 故事必须保证在 **预期/默认路径** 下，于账本可能耗尽前可达成胜利；并必须在 **`MaxRing` 内**宣告胜利。
  - **Fatal（内容/配置错误）**：校验器或运行期判定「作者承诺被破坏」——例如开局凑不出 4 名可上阵角色；跑完 `MaxRing` 环骨架仍未宣告胜利；在默认路径下胜利条件不可达。中止并强日志（seed、storyId、账本、环进度、定义版本摘要）。宿主 **不做** 玩法层补锅（不偷偷允许重复已入账内容、不插入通用终局战等）。
  - **Recoverable 终局（玩家合法路线枯竭）**：玩家按规则把 **环推进所必需** 的事件/战斗可投放面抽干，导致下一环骨架无法生成，且故事尚未宣告胜利 → 可见提示 + 只能放弃/结算，**不** Fatal。
  - **空 Reward 不是终局**：细粒度奖励抽不出合法结果时允许发 0 / 跳过（加诊断日志）；继续环流程。

### 4.2 环结构所有权

- **全局默认骨架**（如环数、每环事件次数、何时出战）由宿主常量 / 默认配置提供。
- **故事脚本**可在 **白名单** 内覆盖（例如 `MaxRing`、每环事件数、某环强制战、单人 Reward 次数 K 等）。
- **`RunController` 独占**：阶段切换、账本写入、胜负结算、失败回滚、存档门闩。

### 4.3 Run 账本（去重与可重复）

- 记录 **`ExperiencedBattles`** 与 **`ExperiencedEvents`**：已不可逆经历的战斗 / 事件（稳定注册 id）。
- **写入时机**：
  - **战斗**：仅当 **胜利** 且进入不可逆结算（如 `BattleEnd → RingEnd`）时写入；**失败回滚不入账**，同战可再遇。
  - **事件**：选项真正生效（进入 Reward 且宿主不可逆提交）时写入。
- **曾刷新为可选项但未执行**：不入账本，可再次出现。
- **卡牌与道具（药水）**：允许重复刷新（统计可与账本分离）；卡牌重复另见升级链规则（4.6）。
- **角色投放**：受潜能满值移出随机池约束（见 4.5）；与账本去重相互独立。

### 4.4 战斗失败与 Run 胜负

- **战斗失败**：回滚至战前 Run 快照（含战中已消耗的药水、金币、**修饰 charges** 等 **全部恢复**），回到可调整编队的 Event（或等价阶段），不写入 `ExperiencedBattles`；可再挑战。失败成本仅为 **时间**（纯时间成本、无限重试）。
- **Run 真正结束（失败侧）**：
  - 玩家主动放弃 / 回主菜单；**无「血量归零式」强制 Game Over**。
  - 或 **Recoverable 终局**（见 4.1：环骨架无法推进）。
- **Run 成功结束**：故事脚本在宿主 **不可逆提交点** 宣告胜利 → 结算 → 回主菜单。允许的时机包括：事件选项生效、战斗胜利结算、`RingEnd` 等；**禁止**在选项预览、失败回滚路径上宣告。
- **`MaxRing` 跑完未胜利**：按 4.1 视为 **Fatal**（作者未履行胜利宣告），与 Recoverable 终局分轨。
- **持久压力**（无跨战斗伤残、无失败资源税）：账本去重、卡牌升级链、角色潜能、金币/共享修饰等路线向累积；开战恒满血；非战斗可随时构筑。

### 4.5 角色池、潜能、被动、开局与换人

#### 4.5.1 池与唯一性

- **开局无预置已拥有角色名单**；`CharacterPool` 由故事脚本与 Run 中途奖励填充。
- **定义级唯一**：池内同一角色定义最多 **1** 个实例；不允许同定义多实例平行养成。

#### 4.5.2 潜能（现行模型：团体潜能，2026-09-19 起）

> **【2026-09-21 合并】**：原「每实例整数潜能 `[0, 100]` + 六档阈值」模型已被 **团体潜能** 取代，历史文本见 §4.5.6。实现细则（团队池、槽位账本、消费/返还、联机表决、存档 schema v2）见 [Run 规格「团体潜能」](./2026-06-22-run-mod-design.md)。

- **团体资源**：`TeamPotentialPool` 全队共享；消费记到**玩家槽位**账本——`PotentialDirectCredit`（直充余额）+ `PotentialSpent`（消费流水，逐笔）。切换角色不丢数据。
- **潜能本身无数值加成**，仅作为被动解锁条件。
- **被动定义**：`CharacterDto.passives: [{buffId, requiredPotential}]`；`requiredPotential` 即解锁成本，**档位为任意数值**（不再限定六档），`0` = 默认解锁。
- **消费顺序**：先扣本槽位直充（无需表决）再扣团队池；跨来源拆多笔记账，每笔记录来源（credit / pool）。
- **返还**：按笔（同一角色实例 + 同一被动的**全部**流水）**原子退回原来源**（直充回槽位、池回团队池），对应被动自动重锁。跨来源拆账的消费**不允许部分返还**——部分返还留下"打折解锁"漏洞（解锁判定只看是否存在匹配流水）。
- **重复获得**同一角色定义：定义级唯一（§4.5.1），不入第二实例；转化为 **`+20`** 入账——若重复的是**该槽位自己已有**的角色则**直充该槽位**，否则进**团队池**。接线在 `RunController.AddToCharacterPool`。
- **潜能满值移池（状态）**：旧模型「实例潜能 ≥ 100 后移出随机角色投放池」依赖已废止的整数潜能，当前**无对应实现**；角色投放的唯一性与去重由 §4.5.1（定义级唯一）与 §4.3（账本）承担。是否要为"满值角色"重设投放抑制，列在 §6 开放项。
- **落盘**：Run 存档 schema **v1 → v2**（新增池与账本字段，`RunDto.Normalize()` 迁移老档）。
- **联机**：`multiplayer.potential.consume_mode`（`free` 缺省 / `vote`）+ 每环每槽位提议次数上限；表决经 `IPotentialProposalApprover`（单机直接放行，联机协议后置）。细节见 Run 规格。

#### 4.5.3 被动解锁与触发（现行）

- **解锁判定**：存在匹配 `(characterInstanceId, buffId)` 的消费流水（或成本为 0）即视为已解锁；**返还即重锁**。
- **载体**：被动统一以 **buff** 为唯一载体，经技能管线释放；**禁止**为被动单独开直写战斗状态的通道（见 2.2）。
- **触发点**：`onWaveStart` / `onTurnStart`（支持 `turnInterval: N` 按波内回合分档）/ `onActiveSkillCast` / `onSlotCardPlayed` 等，由 buff 运行时统一分发；见 [战斗规格「buff 运行时」](./2026-07-21-combat-system-design.md)。
- **开战注入**：`RunController.StartBattle` 按各角色**已解锁被动**（槽序 + `requiredPotential` 低 → 高）构造 `BattleStartBuffEntry`，在 BattleStart 管线中于技能注入之后、冻结 SharedHp 之前挂载（总顺序见 §2.2）。
- **阈值档位不限六档**（任意数值）；旧「六档」限制已废止。

#### 4.5.4 开局 Init

- 每个槽位一次 **角色 3 选 1**；落选作废；选中角色进入共享池并上阵对应槽。开局池内仅此 4 人。
- **硬去重**：候选项生成时排除池中已有及本局 Init **已选**角色；开局不可能「重复拿到」同一角色（避免转化潜能导致某槽无角色）。
- **池不足时降级**：若剩余可候选定义凑不满 3 个，改为 **2 选 1** 或 **1 选 1**（仍硬去重）。故事开局可抽池 `< 6` 时校验器 **强警告**（理想上每次都能凑满 3 选项）；若全程凑不出 4 名可上阵定义 → **Fatal**。

#### 4.5.5 中途与换人

- **中途角色奖励为一等成长**：扩池 / 换人 / 潜能推进是故意的队伍成长通道，不是客串污染。
- **中途**：角色类型奖励按 4.5.1–4.5.2 入池或转化为潜能后，方可在允许时机换人。
- **换人门闩**：仅 **环间 / 特定事件**；**战斗中不可换人**。换人后下次开战按新上阵重算 `MaxSharedHp` 并补满。
- **新人入池**：其初始卡按 4.6 **写入共享 `CardCollection`** 并自动编入该角色卡组；升阶时 **全队卡组**（含板凳）自动替换——接受由此推高共享收集。强力初始卡应配置 `ownerCharacterId` 专属，**不**在宿主为板凳开例外。
- **进入战斗硬约束**：4 个槽位均有上阵角色，且控制权全部分配（单人本地亦满足槽位模型）；每槽卡组通过 4.6 开战校验。

#### 4.5.6 历史：整数潜能模型（2026-09-19 已被取代，仅作参考）

> 以下为 §4.5.2 / §4.5.3 的旧文，**不具效力**，保留仅为让旧讨论与旧存档可解读。现行模型见 §4.5.2–4.5.3。

- 局内每个角色实例维护 **潜能解放** 整数，范围 **`[0, 100]`**（Run 内属性，非局外成长）。
- 潜能 **本身无数值加成**，仅作为被动解锁条件。
- **首次入池**：潜能 = 0。
- **重复获得**同一角色定义：不入第二实例；转化为该实例潜能 **`+20`**，结果 **`clamp` 到 100**。
- **潜能已达 100** 后再收到重复角色：**静默吞掉**（无补偿奖励）。
- **潜能达到 100**：该角色 **移出随机角色投放池**（不再被常规随机奖励抽到）。非随机点名来源若仍发来，按上条静默规则处理。
- 每条被动的 `requiredPotential` **只允许** `0 / 20 / 40 / 60 / 80 / 100` 六档。
- 当实例潜能 `>= requiredPotential` 时该被动视为已解锁。
- 已解锁被动 = 可自动释放的技能。
- **首发触发时机**：仅 **BattleStart**；对每名上阵角色的已解锁被动各尝试触发一次。

### 4.6 卡牌收集、升级链与构筑

#### 4.6.1 收集模型

- `CardCollection` 为 **解锁 / 配方**（可保留链上多阶 id，供图鉴与校验），**不是**稀缺实体库存。
- **单人与联机均为全队共享收集**；联机不把收集池拆成私有。
- 已解锁卡可被 **多名** 满足限制的角色编入各自卡组（各卡组独立一份「可编入」语义，非抢同一实体）。

#### 4.6.2 使用限制（校验顺序）

1. 若存在 **`ownerCharacterId`**：仅该角色可编入（角色专属；开局初始卡多为专属）。
2. 否则按 **`ERole`** 职业限制。
3. 专属卡与职业卡均走同一套升级链逻辑。

#### 4.6.3 升级链与投放

- 构筑时：同一升级链 **只能编入当前已解锁的最高阶**；低阶不可与高阶并存于卡组。
- **每角色卡组内** 同一卡牌 id **最多 1 张**。
- **奖励投放只投放升级链的最低 id**。
- **重复获得**该最低 id → 该链已解锁进度 **升级一阶**（收集可保留多阶记录；可编入变为新的最高阶）。
- **升阶瞬间**：所有角色卡组中该链的旧阶 id **自动替换**为新的最高阶 id（图鉴/收集仍可保留多阶记录）。
- **已达链最高阶** → 将该最低 id **移出投放池**。

#### 4.6.4 开局初始卡

- 角色进入池 / 上阵时：将其初始卡 id **写入共享 `CardCollection`**（经升级链规则归一），并 **自动编入该角色卡组**。
- 专属初始卡即使在共享库中，也无法给其他角色使用。

#### 4.6.5 构筑时机与卡组尺寸

- **非战斗阶段**可随时显式构筑（将收集编入 / 移出各角色卡组）。
- **开战硬校验**：每槽卡组须满足专属 / `ERole` / 升级链最高阶 / 每 id≤1，且张数在 **[1, 10]**（写死）；否则拒绝开战。
- **构筑持久化门闩**：不允许将卡组 **保存 / 确认** 为无法通过开战校验的状态。编辑 UI 内可有临时非法中间态；**离开构筑界面或环推进前** 必须通过与开战相同的校验（避免玩家自致软锁）。

### 4.7 奖励分发（单人 / 联机分叉）

- **设计目标**：奖励切割为 **细粒度、多次随机**；不合并成「一份统筹大礼包」（合并会严重限制奖励设计）。
- **单人**：奖励 **不绑槽**——每次 Reward 默认 **K=3** 次细粒度奖励（宿主默认；故事可白名单覆盖），结果进入共享层（`CardCollection` / `SharedGold` / **共享 Run 修饰** 等）。开局每槽角色 3 选 1 为 Init 特例，不视为常规绑槽发奖。
- **联机**：奖励 **绑槽**分发；卡仍进共享 `CardCollection`，金/修饰等可按槽。框架须能切换这两种策略。
- **金币**：作为细粒度奖励类型之一；**首发仍投放**并累积 `SharedGold`（单人）。完整商店 / 花费面见 **商店·道具规格**（即将补齐）；在花费面落地前金币默认视为 **不可耗尽** 的奖励类型。
- **空 Reward**：某一细粒度抽取若当前可投类型/池已空，该次发空（允许 `K` 次中部分或全部为空），**不**用其它类型强行凑数；加诊断日志；不触发终局（见 4.1）。
- **共享 Run 修饰**（权威模型）：
  - 条目 = **开战时释放的技能引用** + `charges`，走技能管线；**不是**直写战斗状态的 `float` 数值袋（废除 run-mod 旧「冻成 Dictionary 注入 ASC」表述）。
  - 单人进 **共享列表**；联机可挂槽。须绑单角色的强度应做成角色被动/专属卡，而不是单人槽修饰。
  - **`charges`**：配置时 `charges <= 0`（约定 `-1` 或 `0`）= **Run 常驻**，永不扣减；`charges >= 1` = 消耗型，于 **战斗胜利不可逆结算** 时 `-1`，若结果 `< 1` 则 **从列表移除**（耗尽态不得写回常驻哨兵 `0`）。失败回滚恢复战前 charges（见 4.4）。
  - BattleStart 触发序见 2.2。
- **Heal 奖励**：**废除**（非战斗无 SharedHp，开战恒满血，无合法结算目标）。战前增益应显式使用修饰或开战技能。
- **药水 / 道具奖励与使用**：细则外移 **商店·道具规格**；本规格仅要求失败回滚快照含药水状态（若已实装）。

## 5. 错误处理、日志、持久化与测试

### 5.1 错误分级

- **致命（Fatal）**：状态机 / 存档一致性被破坏；或 **内容自洽失败**（见 4.1：如 `MaxRing` 内未宣告胜利、开局凑不出 4 人、默认路径胜利不可达）→ 中止并强日志（含 seed、storyId、环进度、账本、定义版本摘要）。
- **可恢复（Recoverable）**：
  - 非法 id、脚本 DTO 校验失败、单次内容生成失败 → 拒绝提交 + 兜底（须有重掷上限）+ 可见提示。
  - **环骨架无法推进**的玩法终局（见 4.1）→ 可见提示 + 只能放弃/结算（非崩溃）。
- **软失败（Soft）**：非法技能无操作、非法 Buff 不挂载、执行阶段空放牌、未实装费用类型拒绝入队、潜能已满时重复角色静默吞掉、空 Reward 发 0 等 → 继续 + 可开关诊断日志。

### 5.2 日志与轨迹

- 记录：不可逆选择、阶段切换、战斗关键结算（含重定向 / 跳过 / 自动取消原因）、潜能转化 / 卡牌链自动替换、修饰 charges 扣减与移除、空 Reward、Recoverable 终局原因。
- 脚本异常：捕获并记录脚本栈与宿主上下文；默认不让脚本崩溃拖死主线程。

### 5.3 持久化：两类存储（Run + 全局）

#### 5.3.1 Run 存档（单次闯关）

建议最小字段集合包含：

- `seed`、`storyId`、环 / 进度  
- `ExperiencedBattles` / `ExperiencedEvents`  
- 角色池（含**团体潜能池与槽位账本**：`TeamPotentialPool` / `PotentialDirectCredit` / `PotentialSpent`；schema **v2**，`RunDto.Normalize()` 迁移 v1 老档）、上阵、各角色卡组、`CardCollection`、RNG 流状态  
- 单人共享修饰（含每条 `skillRef` + `charges`）/ 共享金（及联机槽数据）  
- 当前阶段与未提交选项（若存在）  
- **定义版本**：各管理器内容版本 / 哈希；加载不一致须提示风险  

#### 5.3.2 全局存档（跨 Run）

与 Run 存档分离，包括但不限于：设置、图鉴 / 统计、**内容池解锁**等元进度。

- **禁止局外数值成长**（无跨 Run 永久攻击、HP、金币加成、潜能等）。潜能仅存在于单次 Run。
- **故事包 gated**：角色 / 卡的投放随 **已选（或已解锁）故事包** 释放；跨故事遭遇可进图鉴 / 统计，但 **不自动** 进入其它故事的投放池。故事脚本本身亦可有解锁门闩。
- 不同文件 / 存储键；原子写 + 备份槽（实现期细节）。
- 需 schema 版本与向前迁移；对 Mod 敏感字段记录内容版本。

### 5.4 测试策略

- **单元测试（C#）**：账本门闩、环阶段流转、升级链投放 / 自动替换 / 构筑门闩与校验、角色重复→团队池 / 槽位直充转化、~~被动阈值六档~~（**2026-09-19 起由团体潜能账本测试取代**，见 [Run 规格「团体潜能」](./2026-06-22-run-mod-design.md)）、修饰 charges / 失败回滚、空 Reward、Fatal vs Recoverable 终局分轨、战斗规格所列队列 / 经济 / 主动计数器性质。
- **确定性测试**：固定种子下关键路径可复现（含 BattleStart 被动→修饰顺序）。
- **集成冒烟**：管理器加载 → 开 run（含开局选人降级与硬去重）→ 环闭环 → 不可逆写入 → Run / 全局存档读写。

## 6. 开放项（不阻塞本规格）

- 敌人 AI / 意图展示与难度曲线（战斗规格可先留最小 AI）。
- 非法内容兜底的精确优先级与玩家可见文案键。
- 各脚本语言宿主的 API 表与沙箱资源上限。
- 真联机协议与掉线策略（架构预留已承认，实现另开规格）；联机共享收集下的选卡/构筑冲突 UX；团体潜能的联机表决网络同步（`IPotentialProposalApprover` 联机实现）。
- 非 Energy 费用类型（Health / Gold / Discard / X）的专项规则。
- **商店 · 道具（药水）规格**（金币花费面、药水库存与使用时机）。
- 故事脚本白名单可覆盖字段的完整列表。
- **潜能消费玩家 UI**：解锁 / 返还当前只有调试面板可达，正式界面未实装。
- **重复角色的正式奖励管线**：`+20` 转化已接 `RunController.AddToCharacterPool`，但角色获取（战斗奖励 / 商店 / 事件）发放重复角色时的调用方接线未实装。
- **满值角色的投放抑制**：旧「实例潜能 ≥ 100 移出随机池」随整数潜能废止，是否需要新的等价规则待定（见 §4.5.2）。
- Recoverable 终局与放弃流程的结算 UI / 统计是否计入「完成」。
- 元素克制 / 抗性：`Element` 维度已贯通全部伤害通道，但仍无消费方（见战斗规格）。
